# Supabase 접근 정책(RLS) 검토 — 닉네임 방식의 한계

- 검토일: 2026-11-03 (KST)
- 방법: README 의 정책 SQL 읽기 + 공개(anon) 키로 **읽기만** 해 본 결과 (쓰기·삭제는 시도하지 않음, 닉네임 값은 기록하지 않음)

## 확인한 사실

| 테이블 | 정책(README 기준) | 공개 키로 읽은 결과 | 판단 |
|---|---|---|---|
| `favorites` (담아둔 곳) | 읽기·넣기·지우기 모두 `true` (누구나) | 전체 행 **6건**을 읽을 수 있음 | ⚠ 누구나 모든 사람의 목록을 읽고, 지울 수 있는 구조 |
| `visits` (오른 오름) | 읽기·넣기·지우기 모두 `true` | 전체 행 **23건**(서로 다른 닉네임 3개)을 읽을 수 있음 | ⚠ 같음 |
| `visit_photos` (인증사진) | 본인(`auth.uid()`)만 | 공개 키로는 **0건** | ✅ 보호됨 |
| 저장소 `oreum-photos` | 비공개 버킷 + 본인 폴더만 | 공개 주소로 접근하면 거절(400) | ✅ 보호됨 |

## 왜 문제인가

- 공개(anon) 키는 배포된 화면(JS)에 들어 있어 누구나 얻을 수 있습니다(원래 공개용 키).
- `favorites`·`visits` 는 정책이 `using (true)` 라서, 그 키를 가진 사람이 **전체 목록을 읽고**, 닉네임을 몰라도 **다른 사람의 행을 지울 수** 있습니다. 닉네임 `이름#번호` 는 화면에서는 "내 목록의 주소"지만 서버에서는 인증이 아니라 단순한 글자 칸입니다.
- README 에도 "실습용(누구나 읽고 쓰고 지울 수 있음)"이라고 적어 두었던 부분이며, 이번 확인으로 실제로 그렇게 열려 있음이 확인되었습니다.
- 인증사진은 처음부터 익명 로그인 + 본인 정책으로 만들어 안전합니다.

## 개선안 (아직 적용하지 않음)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 익명 로그인으로 통일** | `favorites`·`visits` 도 `user_id = auth.uid()` 본인 정책으로 변경(인증사진과 같은 방식) | 가장 안전, 코드 구조도 일관 | 닉네임 `#번호`로 다른 기기에서 이어보던 기능이 사라짐(기기마다 다른 사용자) |
| **B. 함수(RPC)로만 접근** | 테이블 직접 접근을 막고, `닉네임`을 인자로 받는 함수 3개(조회·추가·삭제)만 공개 | 닉네임 이어보기 유지, 전체 읽기·일괄 삭제 차단 | 닉네임+4자리 번호만 알면 접근되는 한계는 남음(약한 비밀번호 수준) |
| **C. 지금처럼 두고 안내** | 한계를 화면·README 에 명시 | 변경 없음 | 위험은 그대로 |

과제 규모에서는 **B**(기능 유지 + 가장 큰 구멍 차단)를 권하고, 제대로 된 서비스라면 **A**입니다. 적용하려면 Supabase SQL 을 실행해야 하므로 먼저 어느 안으로 갈지 정한 뒤 진행합니다.
